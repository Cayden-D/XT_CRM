# 1688 客服绩效与客户经营规划

> 编写日期：2026-10-14
> 依据：产品宣传图 6 张（客户管理维护 01–06、客服能力、绩效方案、未下单追踪、数据报表、分时承压）与《绩效管理解决方案》API 文档 v2.7（2026-05-27）。
> 状态：P1（绩效应用授权隔离与指标口径设置）已实现并通过模拟网关/真实数据库验证；其余阶段为规划。所有接口行为在真实授权联调前均视为“文档声明”，不视为已验证。

## 0. 结论摘要

1. **绩效应用是第二个独立 1688 应用**：独立 AppKey/Secret/回调、独立授权记录、独立令牌刷新，代码层用“应用用途”强制隔离，商品令牌不可用于绩效接口，反之亦然。
2. **数据底座 = 子账号 + 旺旺会话 + 订单 + 退款**。宣传图中的客服对比、排行榜、分时承压、聊天分析、绩效方案、工资表全部由这四类数据在 CRM 内计算，平台不直接提供“绩效”结果。
3. **客户管理以“平台买家 → CRM 客户”绑定为核心**，复用现有 `accounts/contacts/activities/tasks`，新增标签、分层统计、跟进计划与未成交池。
4. **能力边界**：买家发出的聊天内容平台已脱敏（只给长度，内容为 `---***---`）；手机号只能按“使用场景”逐次解密且有日配额；文档中没有语音外呼、客服在线/考勤状态接口。这些限制直接决定了哪些宣传图功能做、怎么做、做不了。
5. 分 7 个阶段交付（P0–P6），每阶段都可单独验收；先打通授权和数据同步，再做指标，最后做工资与营销。

## 2. 绩效应用 API 清单与注意事项

| 接口 | 用途 | 关键限制（文档） |
| --- | --- | --- |
| `alibaba.account.basic` | 授权后识别主账号、连接测试 | — |
| `alibaba.subAccount.list` | 客服（子账号）名单 | 子账号授权时只返回主账号，**必须用主账号授权** |
| `wangwang.chat.relation.query` | 每个客服在时间窗内的会话对象列表 | `page/size` 分页，`size≤80`，**每次查询最多前 2000 条**，超出需缩小时间窗；返回 `cid`、`openUid/adminOpenUid`（1688 买家）或 `taobaoNick`（淘宝用户） |
| `chat.msg.query`（**增值**） | 单个会话的逐条消息 | `count≤100`，`nextCursor + hasMore` 翻页；**买家消息内容脱敏**，仅有 `length`；同一 `cid` 可能混有多个子账号，需按 `receiverLoginId/senderLoginId` 过滤；`messageTypes` 区分自动回复/转交/系统/广播等；`words` 返回命中的关键词 |
| `wangwang.keyword.query.list / add / delete` | 关键词库（如“退款”“差评”“发票”） | 平台侧关键词，CRM 需与本地配置同步，非并发安全 |
| `wangwang.inqury.message.feedback` | 消息后续行为反馈 | 文档仅列名称，无参数说明，**本期不接入** |
| `alibaba.trade.ec.getOrderList.sellerView` | 订单增量同步、按买家 openUid 查订单 | `pageSize≤20`；按 `modifyStartTime/modifyEndTime` 增量；`buyerMemberId` 可传 `buyerOpenUid` |
| `alibaba.trade.ec.getOrder.sellerView` | 订单详情（物流、备注等） | 加密场景，收件人联系方式脱敏 |
| `alibaba.trade.contact.decryptList` | 短信触达时解密手机号 | 必须填写 `useScene`（催付/发货/好评/关怀/上新/活动/召回）与 `message`；**有日调用配额**；结果不得长期保存 |
| `alibaba.trade.refund.queryOrderRefundList` / `OpQueryOrderRefund.sellerView` / `OpQueryBatchRefundByOrderIdAndStatus.sellerView` | 退款金额扣减、售后聊天识别 | 列表“可能有延迟”；页码从 0 开始 |
| `alibaba.product.list.get / product.get / category.get` | 订单商品补全 | 与商品应用重复，**绩效侧只读，不写商品** |
| `app.order.get` | 服务市场订购状态 | 文档仅列名称；用于检查“增值”能力是否订购，联调后再接 |
| `wangwangnick.openuid.decrypt` | openUid → 旺旺昵称 | 文档限定“仅可用于唤起旺旺”，**禁止落库或展示列表**，只在点击“联系买家”时即时调用 |
| `loginid.openuid.encrypt` | loginId → openUid | 用于将订单 `buyerLoginId` 与会话 `openUid` 对齐，联调确认后接入 |

**实测接口行为（2026-10-14 主账号只读抽样，与文档不同处）**：
- 旺旺接口返回顶层 `{success, data}`，没有 `result` 包裹；`alibaba.subAccount.list` 字段在顶层，子账号 `loginId` 形如 `主账号:名称`。
- 会话列表中的 `loginId` 已脱敏（两个字符），不可用；`openUid`/`adminOpenUid` 正常返回。
- 消息的 `senderLoginId`/`receiverLoginId` 已脱敏，文档建议的按接收人过滤不可行；`selfLoginId`、`buyerOpenUid`、`buyerAdminOpenUid` 在**每条消息**上，按 `selfLoginId` 可正确区分同一会话中主/子账号的消息。
- 消息 `time` 为北京时间字符串 `yyyy-MM-dd HH:mm:ss`，`length` 为字符串；客服侧 `length` 为 0。
- 实际出现的消息类型：正常消息、其他消息、系统消息；客服侧“其他消息”正文为空。
- 主账号本身承担大量接待（近 7 天 1,864 个会话），子账号接待很少。

**买家身份对齐**：会话只给加密 `openUid/adminOpenUid`，订单给 `buyerID/buyerLoginId`。归因前需建立统一买家键：优先 `adminOpenUid`（同一主账号的子买家合并），否则 `openUid`；订单侧通过 `loginid.openuid.encrypt` 或“按 openUid 查订单”反查。此步必须在真实数据上抽样验证一致率后再上线归因。

## 3. 授权隔离设计（P1 硬性要求）

### 3.1 配置

```
ALI1688_PERFORMANCE_APP_KEY=
ALI1688_PERFORMANCE_APP_SECRET=
ALI1688_PERFORMANCE_REDIRECT_URI=
```

- `server/config.ts` 新增三项可选变量；三项要么全有要么全无，启动时校验。两套应用的 AppKey 相同时拒绝启动。
- 继续共用 `ALI1688_TOKEN_ENCRYPTION_KEY` 加密令牌（加密密钥不是 AppSecret，共用不违反“禁止复用令牌”）。
- 服务端读取 `.env.local`；三项缺一或与商品 AppKey 相同时 API 拒绝启动。

### 3.2 数据与代码（已实现，迁移 `022_1688_performance_app.sql`）

- 绩效连接存放在**独立表** `integration_1688_perf_connections` / `integration_1688_perf_oauth_states`，而不是在商品连接表加用途列：商品侧的草稿、上架、队列等外键在结构上无法引用绩效连接，反之亦然。同一店铺可同时有两条连接、两份令牌。
- `server/integrations/1688.ts` 的 `appCredentials / getGrant / saveConnection / connectionToken / recordOperation` 增加 `purpose`（默认 `product`，现有调用不变），按用途选择凭证与表；连接的 `app_key` 与当前用途 AppKey 不符时抛 `APP_MISMATCH`；刷新令牌使用同一应用的 Secret。
- `server/integrations/1688-performance.ts`：`callPerformanceApi` 只接受绩效连接及第 2 节的只读接口白名单（关键词写入、手机号解密暂不开放）。
- OAuth：`POST /api/integrations/1688/performance/authorizations` 与 `/authorizations/complete`，state 存在绩效专用表，商品授权的 state 无法在绩效回调中使用。
- 验证：`alibaba.account.basic` + `alibaba.subAccount.list`，记录 `account_role`（main/sub/unknown）、主账号与子账号数；子账号授权返回 `SUB_ACCOUNT_GRANT`，提示用主账号重新授权。主子账号判定依据为 `mainUserId`/`mainLoginId` 与授权身份比对，需真实授权后核实字段形态。
- `integration_1688_operations` 新增 `app_purpose`、`perf_connection_id`，商品与绩效调用记录分开展示。
- 权限：`performance:read/manage`（销售经理）、`payroll:read/manage`（财务；管理层只读）。

### 3.3 验收

- 用商品连接 ID 调用绩效接口 → `APP_MISMATCH`；反向同理。
- 两条连接各自刷新互不影响；撤销其中一个不影响另一个。
- 前端“1688 店铺”页分“商品应用授权 / 绩效应用授权”两栏，分别显示状态。

## 6. 同步策略

已实现（`server/integrations/1688-performance-sync.ts`，API 进程内 worker）：

- **调度**：每 `PERF_SYNC_INTERVAL_MS`（默认 15 分钟）为每个已连接的主账号授权店铺排一次增量同步；页面可手动“立即同步”或补齐 7/30/90 天。每店同一时间最多一个任务，租约 5 分钟，过期重试 3 次。
- **调用额度**：开发测试阶段应用流量为 5000 次/天（含所有接口），提交上线后可提升至 10 万次/天。定时同步在当天出现 `gw.Qos*` 或调用数达到 `PERF_SYNC_DAILY_CALLS`（默认 4500）后暂停到次日（北京时间），手动同步不受影响；90 天历史回补约需 2 万余次调用，开发阶段需数天完成，上线后一天内可完成。
- **限流**：平台对应用有调用频率限制（实测并发拉消息时返回 `gw.QosAppFrequencyLimit`）。每店调用按 `PERF_SYNC_MAX_QPS`（默认 4 次/秒）排队，被限流时依次等待 2/5/15 秒重试，不计为失败。
- **历史回补**：“补齐 N 天”只记录回补目标，每次同步先拉新数据，再由近及远补历史并逐日记录进度；被限流或中断后由下一次定时同步从断点继续，已补的天不再重复调用。消息按会话日期由近及远拉取；新补到的人工回复会让该买家的订单重新计算归属。
- **账号**：每次同步先拉 `alibaba.subAccount.list`，主账号也作为客服；不在列表中的账号标记 `present=false`，历史保留。
- **会话关系**：实测平台按**北京自然日**返回（`beg`–`end` 覆盖的每个日期整天返回，与具体时刻无关），因此每个账号从游标（回溯 15 分钟）所在日期起逐日查询（`end` 取当日 23:59:59.999），`size=80` 翻页；单日第 25 页仍 `hasMore`（超过 2000 条上限）时无法再细分，保存已取到的部分并计入 `truncatedDays`。平台只保留近 90 天，最早一天的 `beg` 自动收紧到保留期内。首次同步 `PERF_SYNC_INITIAL_DAYS`（默认 7）天。
- **消息**：只拉会话时间有变化的会话（2026-10-15 起取消“当天会话每小时重拉”兜底：7,393 个真实会话核对显示会话关系时间与最后一条消息完全一致）；定时同步对近 7 天无会话的客服账号每 2 小时才查一次会话列表，手动同步始终查全部账号，从消息游标续传，按 `uuid` 幂等，4 个会话并发拉取（租约最多每 15 秒续期一次）；**按每条消息的 `selfLoginId` 归属客服**，跨日消息归入对应日期。
- **轮次**：消息入库后从已存消息重算两种口径的轮次；算法升级通过 `turns_version` 批量重建，不调平台。
- **订单**：按 `modifyTime` 每天一个窗口、每页 20 单增量拉取（回溯 1 小时），首次 `PERF_SYNC_INITIAL_DAYS` 天；只在付款时间、下单时间或买家变化时重算归属。
- **退款**：按修改时间增量，`dipsuteType=0` 同时取售中和售后退款，金额从分换算为元。
  - 退款列表所有金额均为“分”：`refundPayment`/`applyPayment` 只含货款，运费另在 `refundCarriage`/`applyCarriage`。入库分别换算为元，报表、工资与客户页扣减用 `refund_total`（货款 + 运费），与按含运费的订单总额计算的销售额口径一致（迁移 035）。实测（2026-10-14）：156 个退款成功订单中 62 个的差额恰为运费，修正前少扣了退运费。
- **归属**：每次同步最后按 500 单一批重算待更新订单的 6 种方案。

实测（2026-10-14，近 7 天）：11 个账号、1,897 个会话、18,964 条消息，首次同步约 6 分钟，之后增量约 6 秒。

## 8. 绩效方案的归因规则（9 种全部实现）

统一流程：订单的 `buyerOpenUid` 通过 `perf_buyer_identities` 找到聊天买家，取该买家所有会话中的**人工回复**（不含自动回复、系统、广播、转交；“其他消息”按口径设置）。窗口为下单（或付款）前 `attribution_window_hours` 小时。

| 方案 | 规则 | 状态 |
| --- | --- | --- |
| 1 优先促成下单（默认） | 下单前最后一条人工回复的客服；没有则用付款前最后回复 | ✅ |
| 2 优先促成付款 | 付款前最后回复；未付款或没有则用下单前最后回复 | ✅ |
| 3 只给促成下单 | 下单前最后回复 | ✅ |
| 4 只给促成付款 | 付款前最后回复（未付款不归属） | ✅ |
| 5 订单插旗备注 | 卖家备注中“@客服名”（子账号冒号后的名字或完整登录名）优先；否则按店铺设置的“旗帜编号 → 客服”规则。订单同步带 `needMemoInfo`，保存 `sellerMemo`、`sellerRemarkIcon` | ✅（P9） |
| 6 付款当日有聊天 | 付款当天（北京时间）有人工回复的客服平分 | ✅ |
| 7 下单与付款分成 | 下单客服得设定比例（默认 50%，10–90%），付款客服得其余；同一人或仅一方时 100% | ✅ |
| 8 只给会员所属客服 | 该客户全部订单归所属客服（与是否聊天无关） | ✅（P9） |
| 9 所属与协作分成 | 所属客服得设定比例（默认 50%），促成下单的协作客服（方案1 的人选）得其余；同一人或只有一方时 100% | ✅（P9） |

**所属客服**：客户档案中手动指定的所属客服优先（含“不设置”）；未手动指定时，自动归给该客户最早一笔已付款订单在方案2 下的客服，随历史补齐自动修正；财务可关闭自动指派（关闭时清除自动指派结果）。所属客服变更后，该客户的订单立即重新归属。方案7/9 比例与自动指派仅财务（`payroll:manage`）可改。

9 个方案的结果全部预先计算，财务切换默认方案即时生效，“订单归属”页可对比；窗口或回复口径修改后，订单标记重算并自动排一次同步。退款按订单归属份额扣减（P5 工资单使用）。

实测（2026-10-14）：首次同步近 7 天修改过的 3,431 个订单和 228 笔退款，约 4 分钟；按“分”换算后没有退款超过订单金额，平均为订单金额的 84%。近 6 天下单的 1,225 单中，有 278 单（23%）在下单前 72 小时内有咨询并归属到客服，但占已付款金额的 64%，说明大量小额订单是直接下单。

## 8.1 KPI 与工资计算（已实现）

- **KPI 综合指数**：可选指标为总接待、有效接待率、询单人数、询单→付款转化率、绩效销售额、平均首次响应、平均响应时间、未回复率；比率类按接待人数折算，避免接待量小的账号占便宜。每项以同期最优者为 100 分（越低越好的指标以最小值为满分），按权重加权；无接待且无订单的账号不参与排名；同分同名次。默认权重：接待 20、有效接待率 15、转化率 25、销售额 20、首响 10、未回复率 10。销售经理（`performance:manage`）可修改。
- **工资** = 基本工资 + 提成 + KPI 名次奖金 + 奖惩。
  - 提成 =（当月**付款**的归属订单金额 × 份额 − 当月**退款成功**金额 × 原订单份额）× 提成比例，按现金口径计入付款和退款发生的月份；可为负（当月退款大于销售时）。
  - KPI 名次按当月综合排行，奖金按名次档位；超出档位无奖金。
  - 规则按店铺设置，可为个别客服单独设置底薪和提成；仅财务（`payroll:manage`）可改，管理层（`payroll:read`）只读，销售经理看不到工资。
  - 草稿可反复重算、增删奖惩；锁定后不可修改，规则变更不影响已锁定的工资单；每个客服可查看付款订单与退款扣减明细；可导出 CSV。

## 8.2 客户分层规则（已实现）

- 客户类型：未购买（0 次付款）/ 新客户（1 次）/ 老客户（2 次及以上）/ 忠诚客户（≥ 设定次数，默认 5）。
- 客户等级：累计付款金额 < 白金门槛（默认 1,000）为普通，< VIP 门槛（默认 10,000）为白金，否则 VIP。
- 客单价：< 100 低价值，< 500 一般价值，否则高价值（可改）。
- 购买周期：自定义天数优先；否则购买 ≥ 2 次时为（最近 − 首次付款）÷（次数 − 1）；只买过一次的客户按默认周期（30 天）判断超期，但不参与周期区间筛选。
- 超期未购：最近付款时间 + 周期 < 当前时间；也可按“超过 N 天未购”筛选。
- 未成交客户：有待付款订单（下单未付款）或有咨询但从未付款（咨询未下单）。
- 分层在查询时计算，修改阈值立即生效；购买统计仅基于已同步的订单（按订单修改时间同步，未补齐的历史订单不计入）。
- 暂缓：短信营销（P7 暂缓）。客户附件已在 P10 实现。
